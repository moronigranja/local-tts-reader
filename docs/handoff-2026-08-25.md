## What is proven

1. **Export correctness (host).** jiangzhuo9357/cosyvoice3-0.5b-onnx (int4 LLM
   backbones + fp32 rest, 3.5 GB) + sokuji's corrected pipeline semantics produce
   valid audio end-to-end: 7.64 s WAV, finite, RMS 0.045, peak 0.43, ASR-quality
   provenance upstream (sokuji PR #336). Host CPU (8 threads) RTF **5.83**.
2. **Kotlin port fidelity, deterministic path.** On-device prompt processing matches
   the host EXACTLY: 162 speech tokens (whisper log-mel + speech_tokenizer graph),
   324 mel frames (matcha mel — mean −5.63 device vs −5.76 host; golden-verified
   front-end), spk norm 15.28 vs 14.97 (~2%, kaldi fbank/campplus numerics).
3. **First on-device measurements (S22 Ultra / SM-S908U1, ORT 1.23.2 CPU, 6 threads):**
   - pre-fix run: RTF **22.17** (llm 51 s, flow 163 s, hift 10 s) per 10.12 s audio.
   - after tensor-lifecycle fix: RTF **15.58** (llm 36.3 s, flow 112.5 s, hift 8.8 s).
   - peak RAM: VmHWM ≈ 2.0 GB with stage-scoped sessions (was lmkd-killed at
     ~7 GB when all 14 graphs were resident + tensors leaked); thermal status
     reached 3 (severe) — subsequent runs throttle hard (~7× slower).
4. **Engine-gate verdict (CPU).** RTF 16–22 ≈ 10× over the ~0.5–1×-realtime bar.
   Flow DiT is 72% of cost; no mobile accel path covers it (Vulkan EP / NNAPI /
   LiteRT-LM are LLM-scope → bounded best case RTF ≈ 10–19). Kokoro-82M stays v1
   primary; CosyVoice3 stays gated (decisions #21).

## Open items (next session)

1. **Device audio defect (the active bug).** Device WAV is hot + buzzing: RMS 0.189,
   peak clipped 0.99 (host: 0.045 / 0.43), voicing autocorr 0.19 (host 0.59),
   centroid 5.2 kHz. Instrumentation pins it: **flow output mel mean −0.87 vs prompt
   mel −5.6** — the generated mel is ~5 dB hot, and HiFT amplifies/clips from there.
   The prompt (matcha) port is verified correct, so suspect the flow stage: CFG
   math, cosine t-span/dt, conds/mu fill, or melLen1 slice in `Pipeline.flowGenerate`
   (spike-tts/.../Pipeline.kt). Add a host-side flow-mel stats dump to
   `/tmp/t3/driver.py` (expect mean ≈ −5, prompt scale) and diff against device.
2. **Confirm clean 3-run numbers** after the audio fix — run 2 throttles to ~7×
   slower under thermal status 3; protocol: cool the device (idle 5+ min or reboot)
   before a measurement, treat run 1 after a cool start as the headline number.
3. **Record final decision + close the gate** in decisions.md once audio is verified
   (exact RTF, RAM, thermal table with device, engine tier order, AR watch item).

## Re-running the benchmark (cheatsheet)

```bash
tools/docker-build.sh :spike-tts:assembleDebug
adb uninstall com.moronigranja.localttsreader.spiketts   # keystore regenerates per build!
adb install spike-tts/build/outputs/apk/debug/spike-tts-debug.apk
adb shell "run-as com.moronigranja.localttsreader.spiketts sh -c \
  'mkdir -p files/models && cp -r /data/local/tmp/models/. files/models/'"  # models stay in /data/local/tmp
adb logcat -c && adb shell am start -n com.moronigranja.localttsreader.spiketts/.MainActivity
adb logcat -s T3Spike
adb exec-out run-as com.moronigranja.localttsreader.spiketts cat \
  /sdcard/Android/data/com.moronigranja.localttsreader.spiketts/files/out_run1.wav > out.wav
```
Key repository state: `spike-tts/` (10 Kotlin files: Fft/Bluestein, Mel front-ends,
Qwen2 BPE, ras_sampling, stage-scoped ORT sessions, pipeline, WAV IO, MainActivity
benchmark), `gradle/libs.versions.toml` (+onnxruntime 1.23.2), `settings.gradle.kts`
(:spike-tts).
